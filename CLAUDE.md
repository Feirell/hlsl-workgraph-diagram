# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A dependency-free Node.js CLI (`fs`/`path`/`zlib`/`http`/`https`/`child_process` only, no npm packages) that
reverse-engineers a Direct3D 12 Work Graph's topology from HLSL source and renders it as a PlantUML diagram
(plus PNG/SVG). Two independent parsers (a regex scanner and a real `dxc` compile) feed one shared IR, which
one renderer turns into a diagram.

The whole codebase (code and docs) is LLM-generated by iterative prompt/review cycling - every file starts
with a banner saying so. Comments explain *why*, not *what* (a hidden constraint, a verified real-world
failure mode, a deliberate behavior change from an earlier version) - match that style rather than adding
"what this does" comments. Several docs explicitly log gotchas already hit; read them before re-deriving the
same conclusion the hard way.

## Commands

There is no build step, no lint config, and no test suite (`package.json` has empty `scripts`/`dependencies`)
- this is a plain Node CLI you run directly.

```sh
node generate-workgraph-diagram.js <command> [args...]   # from repo root
node generate-workgraph-diagram.js <command> --help      # per-command flags
```

The five pipeline commands, run in order:

```sh
node generate-workgraph-diagram.js parse-source ./shaders work-graph.ir.json   # regex scan -> IR
# or:
node generate-workgraph-diagram.js setup-dxil                                  # fetch dxc, once
node generate-workgraph-diagram.js parse-dxil ./shaders/WorkGraph.hlsl work-graph.ir.json   # dxc compile -> IR

node generate-workgraph-diagram.js build-puml work-graph.ir.json work-graph.puml   # IR -> .puml
node generate-workgraph-diagram.js puml-render work-graph.puml                     # .puml -> .png/.svg
```

**Verifying a change**: there's no automated test suite, so validate by running the real pipeline against
`examples/simple-pipeline/` and `examples/mesh-culling/` (each has a `README.md` with the exact reproduction
commands, including any non-default flags like `--global-boxes` - check it before regenerating a `gen/`
output, or you'll silently drop a flag the committed example relies on) and/or `fixtures/dxil-parser-fixture/`
(built specifically to exercise edge cases: `#define` resolution, `#if 0` dead code, an optional mesh node).
Diff the regenerated `.ir.json`/`.puml` against the committed ones - the only difference for an
unrelated change should be the version stamp in the `.puml` legend. `puml-render` needs network access (the
public PlantUML server by default) or `--server <url>` pointed at a local instance.

`setup-dxil` downloads a `dxc` build from nuget.org (`dxc.exe` is Windows-only; this tool runs it directly on
Windows and best-effort via `wine`/`wine64` elsewhere). `parse-dxil` needs the `mesh`-pinned build
specifically for a `[NodeLaunch("mesh")]` node (`--dxc-version mesh`) - `stable` can't compile one.

## Architecture

Five independent commands, each its own directory under `src/`, dispatched by `src/cli.js`:

```
                    ┌─────────────┐
   HLSL source ───▶ │ parse-source │ ─┐
   (regex scan)     └─────────────┘  │
                                      ├─▶  IR JSON  ─▶  build-puml  ─▶  .puml  ─▶  puml-render  ─▶  .png/.svg
                    ┌─────────────┐  │
   HLSL source ───▶ │  parse-dxil  │ ─┘
   (dxc compile)    └─────────────┘
                          ▲
                    ┌─────────────┐
                    │  setup-dxil  │   (fetches dxc, once)
                    └─────────────┘
```

The load-bearing design decision is that **`build-puml` never knows which parser produced its input** - both
`parse-source` and `parse-dxil` write the exact same IR JSON shape (`docs/ir-format.md`), and `build-puml`
only ever reads that. This is what let `parse-dxil` get added later as a second, independent way to get the
same IR, and it's the invariant to preserve when touching either parser: don't leak parser-specific data
through `build-puml`'s rendering code, and don't have `build-puml` branch on `ir.generator`.

`src/common/` holds what's shared *across commands*: `ir.js` (`writeIrFile`/`readIrFile`, `IR_VERSION`),
`cli-args.js` (the declarative flag parser + shared `VERBOSE_SPEC`), `logger.js` (`info()` terse default,
`verbose()` gated on `--verbose`), `themes.js`, `text-utils.js` (paren/string helpers), and
`expr-resolve.js` (`resolveExpr`/`resolveIdentifier`/`annotateExpr` - generic arithmetic-expression resolution
against a `name -> definition text` table; used by *both* parsers' own `constants.js`, which differ only in
how they gather that table - `parse-source` walks the filesystem, `parse-dxil` scans every file dxc embedded
verbatim in `dx.source.contents` debug info). This is deliberate, matching this codebase's per-parser
duplication elsewhere (e.g. `NODE_IO_KINDS` is duplicated, not shared, between the two parsers) - each parser
is meant to stand alone; only truly generic, no-filesystem-dependency logic gets factored into `common/`.

### The IR's `{ resolved, source }` value fields

Every numeric/expression attribute (`numThreads`, `dispatchGrid`, `maxDispatchGrid`, `maxRecursionDepth`, a
record's `maxRecords`/`maxRecordsSharedWith`) is `{ resolved: number, source: string|null }` (scalar) or the
per-axis triple form - see `docs/ir-format.md` for the full schema. `resolved` is always the actual number
(from DXIL metadata for `parse-dxil` - dxc's own canonical compiled value, never recomputed; from this
parser's own constants table for `parse-source`). `source` is the original attribute text, `null` whenever it
would just repeat the resolved literal, and - for a scalar field whose expression references a named
constant - has each identifier annotated with *its own* resolved value at parse time (e.g. `"VERT_SEG *
HOR_SEG"` becomes `"VERT_SEG (6) * HOR_SEG (8)"` in the IR itself, not just in the rendered label). That
per-identifier annotation is *not* itself compiler-derived for `parse-dxil` - `#define`s leave no trace in
any compiled artifact, so it comes from re-scanning dxc's embedded pre-preprocessor source text with this
tool's own small evaluator, independent of the (always compiler-derived) `resolved` total next to it.

`build-puml/node-label.js` decides, from `source` alone, whether a scalar field's `= <total>` suffix is
redundant (skipped when the value's already fully visible - a bare identifier/literal, or a `1 * x` identity
multiply) or needed (a genuine multi-factor product, where the total isn't any single factor's own value).

**Doc drift warning**: `docs/ir-format.md`'s "Value fields" section (as of last check) still says
`parse-dxil` "has no constants table of its own" and that per-identifier annotation only applied to
*unresolved* expressions - both were true before `parse-dxil/constants.js` was added and no longer are.
Verify against the code (`src/common/expr-resolve.js`, `src/parse-dxil/constants.js`,
`src/build-puml/node-label.js`) rather than trusting that doc section until it's updated.

### `build-puml`'s options

`src/build-puml/options.js` is the one non-obvious file here: most `--short-*` flags are independent, but
`--short` is shorthand for all of them, and `--short-meta` additionally drops `Grid:`/`Threads:` lines that
can't vary for a given launch mode (coalescing, thread). `--global-boxes` (off by default) and `--global-list`
(on by default) are independent - the legend's global-resource table is shown regardless of either.
